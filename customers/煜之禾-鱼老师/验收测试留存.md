## 2026-07-17 稳定性挂测前的三处深坑修复(v4 终包)

启用 3 天稳定性 cron 时首轮即暴露三个真问题,全部修复并实证后重打 v4 客户包(交付 dmg 已替换,md5 31c275acb97f39d2ff3592896ced87ff):

### 坑1:od CLI 长任务 5 分钟必断线(产品 bug)
- **现象**:`od baokuan scheduled` 跑到 301s 报 `UND_ERR_HEADERS_TIMEOUT` exit=3,daemon 端管线其实还在跑(白干)。
- **根因**:daemon 端点同步跑完管线才回响应头;Node fetch(undici)默认 headersTimeout=300s,先掐。
- **修复**:daemon 4 个长端点(scheduled/account/link/regenerate)改为先发 200 头+每 15s 写一个空格心跳(JSON 合法前导空白),结果出来再写 JSON 体;错误编码为 200+`{error}`,od CLI 的 post 守卫据此 stderr+exit 5,cron 统计的退出码语义不变。
- **实证**:修复后同一轮 **exit=0 dur=325s**(>300s 断线点),runs=[男性情感成长:候选11/处理5/生成5/归档6]。

### 坑2:app 升级会抹掉客户连好的飞书(产品 bug,交付级)
- **现象**:装 v3 后 runtime 引擎 `.env` 的 FEISHU_BITable_APP_TOKEN 被出厂空白覆盖,`od monitor list` 变"暂无监控项"(其实飞书行都在,是引擎查不到)。
- **根因**:`resyncEngineSourceIfStale` 把捆绑 `.env` 直接 cp 盖 runtime——客户每次升级 app,「连接飞书」写入的 token 全被抹掉,采集静默断。
- **修复**:`mergeBundledEnvPreservingRuntime`——runtime 已有键一律保留,只追加捆绑里新增的键(新版引擎仍能下发新配置默认值)。
- **实证**:写回 token → 删 `.od-engine-src-stamp` 强制再 resync → token **保留**(v3 行为会被抹回空白)。

### 坑3:多客户检出同名进程互杀 + IPC socket 全局共享(操作纪律)
- **现象**:裸 `pkill -f WorkBuild` 误伤另一客户检出(open-design/)正在跑的打包进程;两检出 app 同用 `/tmp/open-design/ipc/default/daemon.sock`,并行起会 EADDRINUSE/互掐(曾把进行中的请求 100s 处掐断)。
